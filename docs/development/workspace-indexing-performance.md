# 工作区切换与索引性能

2026-10-23–24。本文记录当前工作树上的机制、可重复实验和适用范围；模块权限仍由
[Architecture](../../ARCHITECTURE.md) 定义，验证规则由 [Quality](../../quality/README.md) 定义。

最明显的增长型开销来自目录分页。SAF 原来每一页都重新向提供器查询整个目录，再跳过
数字偏移；大于一页的目录还不能把完整名称表交给路径解析器。Rust 文件适配器也在每一页
重新读取、排序和摘要整个目录。因此，页大小固定为 512 时，N 个目录成员要付出
约 N × ceil(N / 512) 的枚举工作；SAF 的目录变化还会让偏移跳行或重复。

设备线程栈进一步定位到增量重建的缺失路径放大：`history_scoped` 对每个历史版本试读
不存在的 tombstone，新发现笔记还会逐条试读不存在的 state head；SAF 每个缺失查找都
进行完整实时路径重验，从根目录重新列举成员。完整清单已经证明缺失，这些重复 I/O
会再次形成近二次增长。重建现在使用 `RecordPresence`：完整枚举加上本轮已验证的自身
写入。缺失记录直接得出领域上的无墓碑或 Unattested，存在记录必须读出并接受原有校验。
自身新写的历史头必须覆盖写前清单的缺席，不能因此丢失刚修复的初始历史。

增量入口原来逐个调用文档扫描器，导致现有最多 8 路并发仅用于完整建库。现在整个变更
集合进入同一扫描器，再按来源路径退役旧身份，仍在全部完成后发布投影。受控阻塞测试
复现了旧入口没有文档重叠，修复后观察到 2–8 路且发布时没有未完成写入。

另一个独立开销是已有历史的加载：每条笔记单独读取历史头，再单独读取其对象。
24 条已有笔记的回归实际观察到 48 个单独的平台批次。Rust 解析更快并不能消除这些
平台调用或 Android DocumentsProvider 的文件创建和校验成本。

实现现在把一次目录枚举视为一个有界观察：

- SAF 在提供器连接仍有效时读完一次元数据游标，关闭游标和连接，再通过不透明游标分页。
  游标绑定树、目录、观察和位置，后续页面不重新连接提供器。完整名称表进入原有解析器，
  大目录也能复用名称解析；读、写和缺失路径继续执行原有实时校验。
- Rust 文件适配器只枚举、排序一次成员名称；分页只对本页成员取得实时元数据。
  游标绑定能力、目录和独立观察，不能移用到另一个授权根。
- 两个适配器都只保留未完成观察，最多 16 个、合计约 64 MiB 的估算数据预算；
  SAF 单个元数据观察额外限制为约 16 MiB，Rust 单个名称观察不能超过其总预算。
  超预算、失效、完成后重用和越界都显式报错，不伪装成完整空目录。预算是数据估算，
  不是整个进程的 RSS 限额。缓存不持有跨调用的提供器连接、游标或目录描述符。
- 分页期间新增成员由下一轮全新枚举发现，当前页链不会因为插入而错位。
  Rust 页内的文件大小等元数据仍来自当前文件；消失或不可读的既有成员会使操作失败。
  这里保证同一页链的成员一致性，不声称整个文件库具有跨目录、跨时间的原子快照。
- 已有历史按依赖阶段加载：先读最多 8 个历史头，验证后再读它们引用的最多 8 个对象。
  单条历史读取和批量读取共享同一个对象校验入口。最终头新鲜度校验继续执行；
  发现已列出的历史头消失时拒绝索引，不能据此创建替代历史。

旧的 SAF 数字偏移及无效数字回退、逐页提供器查询、逐页文件系统排序和逐条历史 tip
加载路径已经移除。未增加依赖或存储格式：状态只使用现有平台与标准库，属于适配器的
不透明游标协议；工作区文件、历史记录和同步格式保持原有语义。

写后观察也必须受变更规模约束。原入口在写完少量历史、身份记录后重新枚举它们的整个
父目录；约两万个已有记录让一次小修改付出了第二轮大目录扫描。现在由应用层选择
观察计划：少量写入或大目录内的小部分写入，按最多 8 个确切路径查询；新目录的大批量
导入使用一次批量列举，避免转为数万次逐文件查询。依据既有成员数的前缀范围查询在
找到足够证据时停止，不为选择计划先遍历整个清单。写入目标消失或变成目录时拒绝发布。

新增平台动作 `Inspect` 明确表达只取元数据：输出必须是 `Unknown` 内容摘要，其变更
token 与目录列举一致。原 `Stat`、读取及写入的内容校验和 CAS 仍使用验证后的摘要。
不能把文件系统内容指纹直接换成 mtime token；两者具有不同的授权含义。动作追加在
现有枚举末尾，FFI 双向转换及 Android 执行边界同步更新，没有修改持久文件格式。

编辑的文件替换路径也曾绕过已知句柄，为替换一个历史头重新列出近万个兄弟项。
现在所有写模式都先实时查询缓存中正向句柄的名称，再由原写入器读取实际内容进行
CAS 仲裁和持久字节验证。句柄失效或名称不符才重新按名称列举；只有 create-only
允许把缓存缺席用于尝试分配新文档，原精确名称、碰撞修复和回滚机制继续执行。
100 次不同内容替换的真实 provider 边界测试从 101 次枚举降至 1 次，逐次核对仲裁
内容摘要和持久字节，并验证改名的旧句柄不会接收写入。

同步的另一个增长型成本是反复线性查找基线、墓碑和本地路径。规划及摘要解析现在各自
从本次事实建立借用路径索引；检测远端用户删除时也使用本地路径集合。原向量仍是持久
事实，序列化、首项查找语义、墓碑优先级和删除门槛保持一致。索引只在这次操作中存活。

WebDAV 同一发布批次内成功建立的父目录现在只请求一次。32 个三级同目录文件的
`MKCOL` 从 96 次降至 3 次；全部上传仍受各自 CAS 约束并接受发布后验证。失败的父目录
请求不进入成功集合，下一批次重新观察；中途外部删除父目录仍通过上传失败显式呈现，
没有自动重试覆盖。未增加跨批次目录缓存或并发写入顺序。

Architecture Impact：目录观察由 Android `data` 和 `lomo-platform-fs` 各自的执行边界拥有；
历史分阶段加载和写后观察计划由 `lomo-application` 拥有；`lomo-core` 定义 `Inspect`
执行协议，`lomo-native` 仅转换 FFI。同步查找和 WebDAV 请求由 `lomo-sync` 拥有。
SQLite 仍由 `lomo-store` 管理且可重建，Markdown、身份和历史语义仍由原 owner 管理。
没有新增依赖、权限边界或架构例外。

## 可重复实验

主机诊断通过真实 `WorkspaceSession` 和文件系统执行器，输出每阶段耗时及平台动作数。
参数分别是文档数、每文档笔记数、每根采样次数；默认仍可直接运行。

```bash
cargo run -p lomo-application --example workspace_path_probe --release --locked -- 1200 8 3
cargo run -p lomo-sync --example sync_scaling_probe --release --locked
just perf device workspace --corpus device --backend saf --trace
just build android benchmark workspaceReopen
```

9600 条笔记实验使用两个独立根，每根 1200 个日期文档、每文档 8 条笔记，每根 3 次，
共 6 个阶段样本。该对照在增量并发及缺失路径修复前采集，用于隔离文件系统分页收益。
前后只切换文件系统分页实现，两侧均保留历史批量读取，并使用
同一份诊断代码；测量阶段没有同时运行编译、测试或设备基准。初期混入编译负载的样本
另行保留，不用于下面的对照。

| 阶段 | 修改前 p50 | 修改后 p50 | 耗时变化 |
| --- | ---: | ---: | ---: |
| 首次索引 | 1444.12 ms | 1298.99 ms | -10.0% |
| 切回已有索引 | 277.87 ms | 138.64 ms | -50.1% |
| 无改动扫描 | 258.46 ms | 152.98 ms | -40.8% |
| 新增文档后的扫描 | 622.13 ms | 425.79 ms | -31.6% |
| 已有历史的完整重建 | 1164.58 ms | 1198.17 ms | +2.9% |
| 切换后第一页查询 | 2.60 ms | 2.67 ms | +3.0% |

完整重建没有观察到耗时改善，不能把分页优化扩大为全链路等比例提速。读取并验证所有
历史内容仍是完整重建的实际成本。240 条笔记的另一组调用计数表明，历史批量化使完整
重建的平台批次从 653 降为 413，读取量保持 960 不变；这个计数证明减少往返，不代表
每个平台都有相同的墙钟收益。

主机原始证据位于 `reports/workspace-scaling/`：
`host-9600-fs-before-isolated.json`、`host-9600-fs-after-isolated.json` 和
`host-9600-comparison.json`；早期 240 条笔记的计数在 `host-before.json`、`host-after.json`。
SAF 的 4097 个成员回归验证一次提供器查询即可返回所有页面、外部插入不会遗漏或重复，
新枚举可以看见新增成员。资源淘汰、跨根、游标边界和写入失败的行为由对应契约测试保护。

首次导入仍必须创建稳定身份及初始历史。9600 条笔记语料需要 20400 次持久文件写入，
本次没有通过省略历史或降低校验来掩盖这项成本。首次导入、完整重建和切回已有索引
必须分别衡量。Android Direct 根的另一套 keyset 分页未在本次改动；上述文件系统对照
对应桌面执行器，不能当作 Direct 或 SAF 的设备数据。没有相同语料、后端和设备上的
旧 Kotlin APK 对照，不能据此判定语言重构本身的快慢。

Android 实际执行了 SAF 工作区诊断（5 次首次索引、5 次冷重开、5 次跨库切换和
5 次外部修改后的扫描），设备为 Android 15 的 redroid x86_64、debug APK。
240 条笔记的首次索引 p50 为 4760.69 ms，跨库切换为 243.69 ms，切换后第一页查询为
2.67 ms，外部修改后的扫描为 419.60 ms。首次索引终点包含授权确认到第一张卡片，
切换终点为生产数据调用到 Ready，不能直接比较为相同 UI 耗时。

第一轮冷重开含一次 207946.35 ms 异常值，保留在 `device-after.stdout.json` 中，
不以删样本方式声称改善。随后独立执行 `just build android benchmark workspaceReopen`，
5 次结果为 2231.04–3298.01 ms，p50 3250.73 ms，没有重现该异常；
结果及完整原始样本保存在 `reopen-isolated.stdout.json`、`reopen-isolated-summary.json`
和 `isolated-workspaceReopen-com.lomo.benchmark.test-benchmarkData.json`。
这些是模拟器/debug 相对证据，不能当作真实手机 release 或旧 Kotlin 版本的对照。

大库 SAF 另使用已授权的 alternate 工作区：增加 1200 个日期文档，每文档 8 条笔记，
合计约 9850 条笔记、22754 个物理文件。首次准备曾触发诊断广播超时，失败记录保留在
`saf-large-import-failure.json`；随后通过 UI 准备恢复完成。准备过程包含部分已完成导入，
`saf-large-fixture-preparation.json` 的耗时不能作为首次完整索引样本。安装新版 APK 后的
首次完整历史校验也保留为 `verify-large.json`，与后续稳态切换分开。

写后元数据观察前后的大库 SAF 样本如下，每个场景 5 次。每个 dirty 样本修改一个日期
文档并新增另一个文档，随后验证全部笔记、任务数量和库标记；验证不计入操作耗时。
两轮连续实验各增加 10 条笔记，总量从 9850 增至 9870，并非重置到逐字节相同的语料。
测量阶段没有并行编译或测试。

| 阶段 | 元数据观察前 p50 | 元数据观察后 p50 |
| --- | ---: | ---: |
| 切换已有库到 Ready | 3569.46 ms | 3592.88 ms |
| 无改动扫描 | 3510.76 ms | 3517.00 ms |
| 外部修改后的扫描 | 7905.38 ms | 4371.57 ms |
| 切换后第一页读取 | 7.03 ms | 6.74 ms |

增量扫描耗时减少约 44.7%，切换和无改动扫描没有改善：每轮完整元数据枚举仍约 3.5 秒，
本次没有以未证实的后台缓存跳过外部修改检测。原始样本分别为 `saf-large-final/` 与
`saf-large-inspect/`，对照为 `saf-large-inspect-comparison.json`。所有实验最后恢复 small
工作区为所选目录；这些目录均为测试夹具。

另对同一个 9870 条笔记的 SAF 库测量真实编辑路径。替换句柄优化前后各连续提交 5 次
不同内容，原始数据分别在 `saf-read-write/` 与 `saf-read-write-replacement/`，APK 摘要及
对照在 `saf-read-write-comparison.json`。两轮期间笔记数相同，所编辑的测试笔记正文
逐渐增长，并非逐字节重置；操作计时不含首次激活或事后数量验证，也没有并发编译测试。

编辑提交 p50 从 **3715.95 ms 降至 573.23 ms**，耗时减少约 **84.6%**。优化后 5 次为
571.10–579.71 ms。第一页及后续共 5 页、每页 100 条的投影读取 p50 为 5.93 ms；
5 条历史的 7 次投影查询 p50 为 0.22 ms。两项读取来自 SQLite 投影，不能当作 SAF
原始文件读吞吐量或读取提速对照；实际编辑则包含 SAF 内容仲裁及持久写入验证。
初次激活的校验、编辑提交、投影读取和后续扫描分别保留，不能互相替代。

同步路径索引采用同一 release 主机诊断代码，对相同本地、远端强 token、已建立基线
输入运行真正的流式规划器，每个规模 5 次，逐次要求零意图及完整路径数：

| 路径数 | 修改前 p50 | 修改后 p50 |
| ---: | ---: | ---: |
| 1000 | 4.59 ms | 0.78 ms |
| 5000 | 102.37 ms | 4.64 ms |
| 10000 | 401.74 ms | 9.66 ms |
| 20000 | 1200.14 ms | 22.12 ms |

证据为 `sync-plan-before-isolated.json`、`sync-plan-after-isolated.json` 和
`sync-plan-comparison.json`。该诊断衡量规划 CPU，不包含网络、磁盘持久记录、SAF 或 UI，
也不证明这些规模符合单个持久记录的字节上限。WebDAV 请求减少由真实本地 HTTP 故障
服务器回归验证，不能换算为真实云服务端到端加速比例。

新增回归证据：`absence-red.log` 实际观察到 24 次不存在的 tombstone 读取、2 次不存在的
state head 读取；`absence-final-green.log` 验证二者为零，且投影与冷重建等价。
`own-write-presence-red.log` 复现了只相信旧清单会丢掉本轮修复历史的问题，正向控制随后
通过。`incremental-parallel-red.log`、`incremental-parallel-green.log` 记录增量文档串行退化
及有界并发修复。SAF 线程证据为 `saf-large-java-threads.txt` 和
`saf-large-native-backtrace-root.txt`，采集时临时启用的调试 adb root 已恢复。

写后观察的 RED/GREEN 为 `metadata-inspect-*.log` 与 `bulk-metadata-*.log`，分别保护
少量修改不重扫兄弟项及首次大批导入不转为逐文件查询。
`complete-parent-inventory-*.log` 另复现并保护一次新增 12 条笔记时使用完整清单决定目录
规模，不能误用增量变化清单；观察结果只返回写入项，不扩大 SQLite 增量更新集。`parent-batch-red.log` 实际记录
96 次父目录请求，`parent-batch-green.log` 验证 3 次、全量上传验证和下一批次重新观察；
`parent-failure-control.log` 保护失败父目录不能授权后续兄弟项上传。
路径索引属于行为保持重构，`sync-index-preservation-before.log` 与 `sync-green.log`
记录改动前后规划、墓碑、冲突、CAS 和恢复契约验证，不把编译错误声称为 RED。
`saf-replacement-red.log` 实际复现 101 次目录枚举，`saf-replacement-green.log` 为包含
该资源界限、改名句柄和原内容校验控制的 data 模块套件结果。
